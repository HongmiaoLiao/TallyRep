# TallyRep 产品与 MVP

更新日期：2026-10-29。本文记录产品范围；架构与正式任务见 [ARCHITECTURE.md](ARCHITECTURE.md) 和 [DELIVERY.md](DELIVERY.md)。除当前动作列表外，下面的业务流程尚未实现。

## 产品目标

为个人力量训练和有氧训练提供动作选择、计划配置、过程记录，以及 AI 分析和指导。先满足开发者自己的训练需要，长期希望达到应用商店发布水平，供其他人使用。

核心场景：准备锻炼时打开应用，选择动作和训练计划，记录实际训练，回顾身体与运动能力的变化，并得到之后训练的参考与引导。

## 已确定的范围

- 第一版包含动作选择、训练计划配置、训练过程记录和 AI 分析指导。
- 初版训练数据保存在本机；后续希望通过 Supabase 一类托管服务支持同步，避免自行维护后端基础设施。供应商尚未锁定。
- 日常先在 Windows 开发；Android 是目标平台，MVP 或稳定阶段再集中调试。
- Web 使用示例数据，提供完整交互演示，通过 GitHub Pages 展示。
- 继续使用 Vue 3、TypeScript、Tauri 2、Rust 和 npm。
- 用户自行配置模型 URL、模型名及 API 密钥，客户端直接调用；第一版不增加服务端。AI 范围确定为训练后复盘、下一次建议及用户确认后调整计划。

## 建议的第一版使用流程

1. 从一个小规模的内置动作库中选择动作，支持按名称及力量或有氧类型查找。
2. 创建命名计划，添加和排序动作，填写预期训练量。
3. 从计划开始一次训练，逐项记录实际完成情况，并允许修改记录。
4. 完成训练后保存，查看本次摘要及历史训练；重启应用后仍可查看。
5. 主动请求 AI 根据本次和相关历史记录进行复盘，给出下一次训练的参考建议。

动作类别与记录方式分离：支持负重次数、次数、时长、距离时长四种记录方式，覆盖自重力量、定时力量与有氧；有氧距离可缺省。单位明确，实际记录与预期值分开。训练感受先作为可选备注，其他指标按实际需求增加。

第一版摘要以记录中可计算的事实为主，如训练时长、完成组数、同动作的重量与次数变化。有氧和力量数据分别展示。更广泛的身体健康指标需要相应数据来源，不能仅凭训练日志生成健康结论。

## 计划与实际记录

建议从四类领域对象开始：

| 对象 | 含义 | 初始内容 |
| --- | --- | --- |
| 动作 Exercise | 可重复选择的训练动作 | ID、名称、力量或有氧类型、记录方式 |
| 计划 WorkoutPlan | 可重复使用的训练安排 | ID、名称、有序动作项、预期训练量 |
| 训练 WorkoutSession | 某一次实际发生的锻炼 | ID、来源计划、开始与结束时间、状态、动作快照 |
| 实际记录 | 本次动作的实际完成情况 | 力量组或有氧记录、完成状态、备注 |

开始训练时保存计划内容的快照。修改计划或动作名称不会追溯改变历史训练。预期值与实际值分开，才能比较执行情况。

力量与有氧使用不同的记录结构，避免强行给有氧填写重量和次数。具体 TypeScript 类型、Rust 类型和数据库结构在第一个功能开发时逐步落实。

## AI 教练的初始边界

第一版实现训练后复盘与下次训练建议，保留用户要求的真实 AI 能力。输入是用户选择发送的训练记录和必要背景；输出分为训练摘要、建议及其依据、需要补充的信息。记录里的数值由程序计算，再交给模型解释。

建议由用户主动请求分析，并说明将发送哪些数据。反馈不足时询问补充信息，不编造历史表现。建议可以预览，用户选择后再修改计划；AI 不直接覆盖已完成的记录。

模型不可用或离线时，动作、计划和训练记录仍可使用。真实模型接入是第一版目标的一部分，预设示例不能替代其完成验收。

模型由用户自行选择和付费，客户端使用其配置的 URL 与密钥直接请求，不建设托管调用入口。首版协议以 OpenAI Chat Completions 兼容子集为架构基线，其他协议需要适配。访问远程模型时，用户选择发送的输入会离开设备。密钥独立加密保存或仅本次使用，不写入前端资源、训练数据库或仓库；具体密钥库需要技术验证。

## Web 演示

使用独立示例数据，支持动作选择、计划编辑、训练记录、历史回顾与 AI 结果展示，并提供恢复示例数据入口。演示修改不影响客户端真实数据。

建议 AI 区域采用明确标注的预设示例，展示分析与采纳建议的操作流程，不冒充实时模型分析。自由输入或任意修改的数据不能被宣称已由该预设报告分析。Web 无需登录，不收集真实训练数据，也不嵌入模型密钥。

## 开发顺序与验收

按设计与工程基线、计划管理、本地训练与恢复、真实 AI、Android 与发布候选五个阶段推进。各阶段的任务、依赖、完成定义和首张任务卡见 [交付计划](DELIVERY.md)。第一张正式任务是领域契约设计，不继续扩展临时问候页面。

首轮不增加账号、云同步、社交、支付、穿戴设备接入、自动生成初始计划或视频动作识别。身体指标的具体范围、常用动作、模型兼容性样本及发布商店在对应任务前细化。
