# TallyRep 项目交付计划

日期：2026-10-29。依据 [架构方案](ARCHITECTURE.md) 和 [MVP](MVP.md) 执行。用户担任实现者与产品决策者，助手担任架构师、技术负责人和评审者。当前处于 M0 设计阶段。

## 工作方式

每个任务必须包含目标、依赖、修改范围、接口、验收条件和验证证据。负责人先解释设计约束，执行者实现，随后由负责人评审正确性、边界、可维护性和测试；修改问题后验收。教学围绕真实交付，不继续通过连续复制演示片段推进。

任务状态统一为 Backlog、Ready、In progress、Review、Done、Blocked。Done 必须有代码或文档产物与验收依据。一个实现任务进行中即可；遇到影响契约或存储格式的变化先记录设计决定。范围变更记录影响的任务与验收，不直接扩张当前任务。

任务建议用 0.5～2 个专注工作日的规模拆分；这是切分原则，不是工期承诺。前两个实际任务完成后再估算进度，不根据教学对话速度承诺发布日期。

代码采用短生命周期任务分支与 Pull Request 流程，一次任务一个可评审变更，分支默认 `codex/tr-编号-主题`，无任务编号时使用 `codex/主题`。禁止直接在 main/master 开发、提交或直接推送功能变更；开始修改前检查分支，已有未提交修改先随新分支保留。提交后经评审与所需检查，再通过 PR 合入主分支，不自动合并。

main 保持可构建。初期任务表放在仓库中，确有需要时再迁移 GitHub Issues/Projects；远端分支保护尚未配置，不能将协作约定当作服务端强制保护。当前架构基线在 `codex/architecture-baseline` 分支整理提交。

## 第一张执行任务卡

### TR-001 动作与训练记录契约设计

目标：冻结首轮可实现的领域契约，使下一步数据库和界面开发有共同依据。

执行者：用户。评审者：助手。输出：`docs/contracts/training-v1.md` 与非敏感的 `fixtures/contracts/training-v1.json`。本任务先设计，不改现有应用功能，不安装依赖，不写数据库实现。

输入：现有 Exercise 类型、三条动作、ARCHITECTURE 中的实体与规则。设计顺序是 Exercise → metricKind → 计划目标 → 实际记录 → session 状态。

必须交付：

1. Exercise、PlanTarget、TrainingRecord、WorkoutSession 的字段表：类型、是否必填、单位、默认值、校验规则和归属。
2. 四种记录方式各一个实际 JSON 示例：weighted_reps、reps、duration、distance_duration；明确 pending 时哪些实际值可为空、completed 时哪些必需。
3. session 和单条记录的状态转换表，包含完成、跳过、放弃、重复保存和恢复。
4. API 请求与响应草案：list_exercises、start_session、save_training_record；明确 operationId、expectedRevision、成功结果和错误代码。
5. 至少四个反例：负数次数、计时动作混入重量、无距离的合法有氧记录、同一开始请求重复提交；说明接受或拒绝及理由。

验收条件：

- 计划目标与实际值不共用一个会被相互覆盖的对象；session 明确保存快照。
- 记录类型可由明确标签区分，不需要根据哪些字段碰巧为空来猜类型。
- JSON 示例符合字段表，不含单位含糊的 weight 或 duration；采用约定的克、米、秒。
- 缺失与零分开表达；自重次数、定时力量训练和无距离有氧均可表示。
- Rust 与 TypeScript 能表达同一份契约；主键和 revision 的职责明确。
- 反例和状态表经评审通过，再进入数据库 DDL 与实现。

交付时说明尚未解决的问题，不需要先自行引入通用框架。负责人会先评审模型，再给 TR-003 的实现任务卡。

## 完成标准

文档任务：内容与已有决策一致，示例可解析，边界和未决项清晰，链接有效，经评审。

功能任务：满足任务卡，相关类型和构建检查通过；有针对状态转换、持久化、错误或数据丢失风险的测试；有实际交互证据；更新必要文档；没有凭据、数据库或构建产物进入提交。

前端相关检查使用现有 typecheck/build；Pages 变化增加 build:web。Rust 使用 fmt/check，并在相应任务中加入 clippy/test。当前项目尚未安装前端测试工具，TR-002 确立并锁定版本；浏览器测试优先采用 Vitest 与 Playwright，安装前验证工具链要求。

TR-002 同时明确 `.env`、密钥库、本地数据库及备份的忽略规则，示例配置只保留空值；加入 `@/` 别名时同时配置 TypeScript 与 Vite。提交前检查实际暂存内容，不依赖忽略规则代替审查。

代码评审先看数据正确性和用户流程，再看模块边界、异常处理和维护成本。不以测试数量或覆盖率数字替代关键路径验证，也不为纯布局微调编写镜像式测试。

## 风险与检查点

| 风险 | 处理 | 检查点 |
| --- | --- | --- |
| 模型 URL 并不兼容首版协议 | 文档明确协议子集，模拟与真实端点分别测 | TR-011～013 |
| 密钥库或 SQLite 在 Android 行为不同 | Windows 先验证，Android 阶段独立验收；失败影响发布日期，不能隐藏降级 | TR-016 |
| 数据模型过度简化 | 先用多种记录方式及状态反例验证 | TR-001 |
| 中断丢记录 | 逐次确认落盘，事务、幂等、重启恢复 | TR-007～010 |
| 模型虚构或建议覆盖用户修改 | 确定性摘要、响应校验、版本检查和明确确认 | TR-013～014 |
| 目标范围扩大 | 新需求进入 backlog，标注影响；保留当前验收边界 | 每次评审 |
| 动作内容或模型配置不适合公开发行 | TR-005 导入时完成来源和许可筛选，发布前复核；媒体与数据分别审核 | TR-005、M4 |
